1. CRITICAL: ReferenceError: chalk is not defined
--------------------------------------------------------------------------------
- Affected Files: 
  * src/engines/publicMintEngine.js
  * src/engines/allowlistMintEngine.js
- Symptoms:
  Bot crashed during the countdown timer prior to drop execution with:
  "ReferenceError: chalk is not defined at tick (publicMintEngine.js:213:37)"
- Root Cause:
  The continuous warmup countdown timer called chalk.blue() and chalk.yellow() 
  to render colored console output, but `chalk` was never imported at the top of 
  either engine file.
- Resolution:
  Added `const chalk = require('chalk');` to both engine files and verified 
  colored timer execution.

2. CRITICAL: ReferenceError: chainConfig is not defined
--------------------------------------------------------------------------------
- Affected Files: 
  * src/engines/publicMintEngine.js
  * src/engines/allowlistMintEngine.js
- Symptoms:
  When an on-chain transaction reverted or failed, the terminal displayed:
  "Technical detail: chainConfig is not defined"
  and the final summary table printed "Unknow...nown" for wallet addresses.
- Root Cause:
  The run configuration destructured `chain` from `config`, but the result object 
  construction referenced `chainConfig?.name || network.name`, throwing a ReferenceError 
  inside the broadcast promise handler.
- Resolution:
  Updated destructuring to `chain: chainConfig` and aliased `const chain = chainConfig;` 
  so all network name references resolve cleanly without throwing.

3. HIGH: Double-Increment of Failure Counters (e.g., "6/3 failed")
--------------------------------------------------------------------------------
- Affected Files: 
  * src/engines/publicMintEngine.js
  * src/engines/allowlistMintEngine.js
- Symptoms:
  Progress bar and summary totals displayed inflated numbers exceeding the total 
  wallets loaded (e.g., "Mint Complete: 0/3 successful | 6/3 failed").
- Root Cause:
  When a transaction receipt returned status 0 (reverted), the engine incremented 
  completedCount and failCount. Subsequent errors during return payload creation 
  triggered the outer catch block, which incremented completedCount and failCount 
  a second time.
- Resolution:
  Introduced a per-wallet `hasCounted` boolean guard ensuring each wallet task 
  only increments the progress and failure counters once under any circumstance.

6. DEEP ANALYSIS: Why Public Scheduled Mode Frequently Reverts On-Chain
--------------------------------------------------------------------------------
When using "Public Mint" with the Auto-Scheduler / Scheduled Timing on SeaDrop, 
transactions commonly revert due to 5 on-chain contract mechanics:

1. BLOCK TIMESTAMP DRIFT & SEQUENCER LAG (`NotActive`):
   - The SeaDrop contract enforces: `require(block.timestamp >= drop.startTime, "NotActive")`.
   - When a drop is scheduled for exact second T (e.g., 3:48:03 PM), your local system 
     clock may reach 3:48:03.000 before the blockchain sequencer produces a block with 
     that timestamp.
   - If the mined block carries a timestamp of 3:48:02.999, the contract rejects the 
     transaction with `NotActive()`.
   - Solution / Mitigation: The bot should fire an immediate transaction at T=0, followed 
     by micro-burst retries at T+0.5s, T+1s, and T+2s if NotActive is detected, guaranteeing 
     inclusion in the first block where the drop is live.

2. CUMULATIVE WALLET MINT LIMIT REACHED (`ExceedsMaxPerWallet`):
   - SeaDrop enforces `maxTotalMintableByWallet` across the lifetime of the drop stage.
   - If a wallet previously minted its maximum allowed tokens (e.g. 3/3 tokens in an earlier 
     test or previous block), any subsequent scheduled mint call from that same wallet 
     will immediately revert on-chain with `ExceedsMaxPerWallet(3, 3)`.
   - Solution: Use fresh burner wallets created via `node cli.js --generate` or verify on-chain 
     mint count prior to scheduling.

3. RESTRICTED FEE RECIPIENT MISMATCH (`FeeRecipientNotAllowed`):
   - In SeaDrop, creators can set `restrictFeeRecipients = true`.
   - If enabled, the fee recipient passed in `mintPublic(nftContract, feeRecipient, minter, qty)` 
     MUST be in the contract's `_allowedFeeRecipients` list.
   - If the creator changes this list or uses an unallowed creator payout address, 
     the contract throws `FeeRecipientNotAllowed()`.

4. INCORRECT PAYMENT AMOUNT (`InsufficientPayment` / `IncorrectPayment`):
   - SeaDrop requires `msg.value == mintPrice * quantity`.
   - If the creator updates the drop price shortly before the drop, or if `msg.value` 
     does not match the exact price on-chain, SeaDrop rejects the transaction.
